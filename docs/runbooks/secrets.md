# Secrets management

MVP posture: env vars from a per-environment `.env` file. Keys generated by `openssl`, stored in env vars, never committed. Rotation by re-encrypting affected data with a new key.

KMS (AWS KMS / GCP KMS / HashiCorp Vault) is v2 — out of scope for the 60-day MVP. The crypto helper at [`apps/api/src/crypto/session-secret.ts`](../../apps/api/src/crypto/session-secret.ts) is designed so its call sites don't change when KMS lands.

## 1. The five secrets

| Secret | Used by | Stored in | What it protects |
|---|---|---|---|
| `SESSION_SECRET_MASTER_KEY` | T-208 helper, every endpoint that reads/writes a session keypair | `apps/api/.env` (32-byte hex) | session keypairs at rest in Postgres `sessions.encrypted_session_secret` |
| Treasury keypair | T-215 worker (Dodo → vault transfer) | `apps/api/.env` (base58 secret key) | the treasury hot wallet that funds users' vaults |
| `JWT_SECRET` | T-203 SIWS auth, every dashboard JWT | `apps/api/.env` (32-byte hex) | dashboard auth tokens (24h expiry) |
| `DODO_WEBHOOK_SECRET` | T-215 webhook handler | `apps/api/.env` | HMAC verification of Dodo Payments webhook calls |
| API keys (issued to agents) | T-204 middleware | Postgres `api_keys.hashed_token` (bcrypt/argon2 hash) | per-agent access; only the hash leaves the DB |

API keys are not in `.env` because they are user-issued; the others are infrastructure-level.

## 2. Generation

All hex keys are 32 bytes (256 bits):

```bash
# SESSION_SECRET_MASTER_KEY, JWT_SECRET, DODO_WEBHOOK_SECRET
openssl rand -hex 32
```

Treasury keypair (Solana base58 secret key):

```bash
solana-keygen new --outfile treasury.json --no-bip39-passphrase
# Convert to base58 with @solana/web3.js or use the keypair JSON directly
# in the backend (loaded via Keypair.fromSecretKey).
```

## 3. Where they live

| Environment | Storage |
|---|---|
| Local dev | `apps/api/.env` (gitignored; copy from `apps/api/.env.example`) |
| CI | not present — CI runs lint/typecheck/tests only, no backend boot |
| Staging / production | platform secret store (Fly.io secrets, Railway variables, Render env-vars) — **never** committed |

The canonical list of env vars lives at [`apps/api/.env.example`](../../apps/api/.env.example). Adding a new secret means updating both `.env.example` (placeholder) and this runbook (how to generate + what it protects).

## 4. Rotation

### 4.1 `SESSION_SECRET_MASTER_KEY`

Re-encrypt all session secrets in Postgres under the new key:

```
1. Read all sessions.encrypted_session_secret rows.
2. Decrypt with old SESSION_SECRET_MASTER_KEY using decryptSessionSecret().
3. Encrypt with new SESSION_SECRET_MASTER_KEY using encryptSessionSecret().
4. UPDATE sessions SET encrypted_session_secret = ?
5. Swap env var, restart.
```

A migration script is not yet written — write when first rotation is needed. The crypto primitive at `apps/api/src/crypto/session-secret.ts` is the only encrypt/decrypt path.

### 4.2 `JWT_SECRET`

Rotation invalidates all live JWTs (24h max-age). Coordinate with the team and announce in the team channel — every dashboard user re-signs in.

### 4.3 `DODO_WEBHOOK_SECRET`

Update in Dodo Payments dashboard, then update `.env`, restart. Brief window of webhook failures during rotation — Dodo retries, eventually OK.

### 4.4 Treasury keypair

Generate new keypair, transfer remaining USDC float from old to new, update `.env`, restart. Solana doesn't have a "revoke"; abandonment is the mechanism.

## 5. Leak response

| What leaks | Containment |
|---|---|
| `SESSION_SECRET_MASTER_KEY` | rotate (§4.1). Bounded blast: with the key, an attacker can decrypt session keypairs, but those are still subject to on-chain caps + recipient allowlists. |
| Treasury keypair | drain remaining float to a fresh wallet, rotate (§4.4). Bounded by the float cap (~$500–1k for MVP). |
| `JWT_SECRET` | rotate (§4.2). All sessions invalidated, users re-auth. |
| `DODO_WEBHOOK_SECRET` | rotate in Dodo dashboard + `.env` (§4.3). |
| API key (single agent) | dashboard → revoke. Hash-only DB leak is not directly usable. |

## 6. Anti-patterns

- **Never commit `.env`.** `.gitignore` already covers `.env` and `.env.*`. The re-allow `!**/.env.example` is only for the template. Verify with `git check-ignore -v apps/api/.env`.
- **Never log secrets.** No `console.log(masterKey)` even for debugging — and especially not in test fixtures.
- **Don't share dev `.env` files via Slack/Telegram.** Each dev generates their own with `openssl rand`.
- **Don't reuse `SESSION_SECRET_MASTER_KEY` across environments.** Dev / staging / prod each have their own.

## 7. v2: KMS

When MVP graduates, the env-var path is replaced by KMS-managed keys:

- Master keys live in KMS; the app calls `kms.encrypt()` / `kms.decrypt()`.
- IAM-controlled access; audit logs in KMS console.
- Rotation handled by KMS automatic re-encryption (or scripted with the same algorithm as §4.1).
- `apps/api/src/crypto/session-secret.ts` becomes a thin wrapper over the KMS client.

The interface (`encryptSessionSecret`, `decryptSessionSecret`) is designed so the swap is local to the crypto module — no call sites change.
